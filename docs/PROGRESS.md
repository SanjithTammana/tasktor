## Interpretations
- **Linux build set.** CI's Linux job builds `Tasktor.Linux.slnf`, a solution filter without `Tasktor.Flyout` and `Tasktor.Widget` (WinUI / Windows App SDK do not build on Linux). The Windows job builds `Tasktor.sln`.
- **`net10.0-windows` projects run on Linux.** `Tasktor.Windows`, `Tasktor.Agent`, `Tasktor.Capture` and `Tasktor.Shell` target `net10.0-windows` (compiled on Linux with `EnableWindowsTargeting`); their test projects target the same TFM and run on Linux. Only code paths that call Win32 need Windows; everything else is tested here.
- **G-net from M0.** The banned-API analyzer (planned for M12/M15) is on from the start for every `src/` project; it costs nothing and stops accidents early. Network use lives only in plugins (outside `src/`).
- **No Flyout / Widget test projects yet.** Their testable logic lives in `Tasktor.Hosts.Common` (renderers, fitter), which has its own test project.
- **Schema ids.** `$id` is `urn:tasktor:schema:<file>` so the repo names no web domain it does not own; files point `$schema` at the shipped schema file (relative path) for editor autocomplete.
- **One schema file per root record.** `tasktor.action/1` is two files (`action-request-1`, `action-result-1`); `tasktor.plugin/1` is four (`plugin-1` manifest, `plugin-input-1`, `plugin-output-1`, `pack-1`). The contract id stays the same; the file name says which record.
- **Conditions and rule actions are flat records.** The rules grammar picks a condition / action kind by which key is present (`metric`, `learned`, `all`, …), not by a discriminator, so `Condition` and `RuleAction` are records with all keys optional; `RulesLoader` (M4) enforces exactly one kind per object. Value-states use `{"state": "fullscreen", "is": "exclusive"}`.
- **Action origins.** `widget`, `flyout`, `tray`, `toast`, `cli`, `rule`, plus `shell` for `tasktor-shell` (U3). Plugin card buttons arrive with the viewer's origin and the `plugin.action` action, which only reaches the plugin's own declared actions.
- **Args and targets are string maps** (`{"mode": "polite"}`, `{"pid": "4242"}`) so every origin (CLI included) sends the same shape.
- **Grouping rules live in `rules.json`.** A2.2 says grouping rules are `rules.json` entries, so `tasktor.rules/1` gained an additive `grouping` list (`match {exe|path|package} → group_as | attach: parent | never`).
- **The seven interfaces live in Contracts** (D-A5 §4) with their value types, so plugins' SDK and viewers share them; `IBlockRenderer` stays in the viewer hosts.
- **Own log sink instead of `Microsoft.Extensions.Logging`.** H6 asks for an AOT-safe logger without personal data; a 150-line `LogSink` with typed `LogField`s (primitives or `Sensitive<T>` only) keeps the agent dependency-free and makes redaction structural.
- **`AppGrouper` system bucket:** a process with no readable path that is not the user's own, plus PIDs 0 and 4, goes to "System / services" (A2.1 step 6).
- **Snapshot publishing is change-driven, not ticked.** D-H3 says ≤ 1/s on change; D-A3 says an idle agent wakes about once a minute. A 1 s timer would wake the agent 60 times a minute, so state updates call `MarkChanged`, which schedules a single publish at max(now, last + 1 s).
- **A toast click is the confirmation.** D-H4 lets a toast run destructive actions "only the toast itself offered" (e.g. `run`, A6's Close). A toast cannot show a second step, so for origin `toast` the offer (registered in `ToastOffers` when shown, withdrawn when the toast goes) replaces the confirm token.
- **The critical denylist blocks every mutating action**, not only End: priority, EcoQoS, caps, close and freeze on `csrss`, `lsass`, `dwm`, `explorer`, `tasktor-core` … are refused; read-only actions (open file location) pass. A3 only promises "End disabled"; changing a critical process's priority is no safer.
- **`preset.apply` is reversible-class but user-only**: U3 lets click / hotkey / `tasktor preset apply` move and launch without a confirm, while rules may only `arrange`. `UserOnly` encodes "never from a rule" (also used for `run` and `plugin.enable`).

- **`plugin check --run` is not sandboxed.** It runs the author's own program once with their rights, without the agent's Job Object (256 MB) — it is a development tool for the plugin's author, said so in its help and in docs/plugins.md. Installing still goes through the consent dialog and hash pinning; nothing in the authoring tools skips them.
- **No plain-text index, ever.** OQ-C22's SQLCipher is bundled (approved); without a working codec the index is not written at all rather than written unencrypted (option (b) of §9 keeps plain terms on disk). Forget by app or host (C21.4) waits for activity documents to carry their apps; forget by time works. Embeddings (gate G8) join the reciprocal-rank fusion later.
- **Personal data over the pipe for presets (owner's decision, 2026-11-07).** The `open_windows` pull carries window titles, program paths and launch arguments to the user's own deep window; every other pull stays names and numbers. It is never logged and never leaves the current-user pipe.
- **History-only commands carry no app.** PSReadLine's file says nothing about which terminal ran a line, so a history line with no matching key run (the keyboard hook is still detached, so today that is every PowerShell command) is recorded with `app` null and actor `unknown`, and the blocks of both PowerShells and of the foreground app apply. The history line is stamped when it is read (at most one 250 ms pump after PowerShell appends it), which keeps it well inside C22.1's one-second window.
- **Forgetting an app or site forgets whole activities.** A document's lines do not say which app they came from, so an activity that included the app or site is forgotten whole (vault document and index rows), and the confirm says so. Records written before sources were tagged name none: they stay until the 7-day retention drops them (pre-release data only).
- **`capture.forget` needs the capture host.** Only the capture host holds the vault's key, so with capture off a time, app or site cannot be forgotten selectively; the action refuses and points at forgetting all capture data, instead of the old "forgot 0".
- **Reopen is web pages only for now.** C §9's link table also names files and window AUMIDs; those come from the UIA source (the capture lane), so only addresses the extension reported are kept, and the launcher is never handed anything but an absolute http(s) address.
- **The switcher enumerates windows in the shell, not the agent.** D-W4 lets titles cross the pipe to the shell; enumerating in the shell itself means no title ever crosses it, and the agent sends only handles (MRU) and pids (badges). The MRU order still comes from the agent's `WinEventSource` (D-W4's lease), so the shell holds no hook.
- **Alt+Tab hook removal guard, approximated.** D-W3 asks to reinstall the hook when ≥ 50 key-like inputs pass with no callback; `GetLastInputInfo` gives only the time of the last input (mouse included), not a count, so the guard reinstalls when input arrived over 30 s and the hook saw no key. A needless reinstall is harmless. Reinstalling on resume and unlock is covered by the same check.
- **Switcher keys.** D-W4's "press → on an app" is read as a key that switches to the app view: Up / Down toggle it (Left / Right and Tab move). Typing or switching views keeps the switcher open after Alt is released (then Enter chooses); a quick Alt+` tap (Alt already up when the window shows) chooses the previous window at once, like Alt+Tab.
- **C22 history across a closed gate (contract agreed with the capture lane).** History lines carry no timestamps, so the boundary is the read: the file is read every tick; lines read while the gate is closed are dropped, and so is everything read on the first open tick after a closed period or a session notice (it may have been written during that period); commands held for pairing are dropped at a notice or a closed tick. Lines first read after that are recorded as usual, so the log resumes without restarting capture (the capture lane's first fix paused it until restart). `tasktor-capture --no-browser` runs a check fixture that accepts no browser data (no browser pipe, no offline queue).
- **A rewritten or recreated history file is judged by content (C22).** PSReadLine's file has no per-line timestamps, and neither file identity nor creation time works across a delete-and-recreate on NTFS (file-system tunnelling keeps the old creation time for 15 s). So the tail remembers hashes of the commands it has seen (the file's own lines at start, at most the last 256 KB, and everything read since, at most 8192) and, when the file shrank or changed under it, takes only the commands after the last one it knows: a PSReadLine trim imports nothing, a recreated file is new from its first line (the capture lane's real-PC check had missed that first command). A file with no known line counts as new only if it was last written strictly after capture started and at or after the previous read (no slack: a coarse file time only makes a file look older, which fails closed) and holds at most 3 commands, what could have been typed since. The guarantee is about when lines were written, not where their text came from: text copied into a freshly written file cannot be told from typed commands (capped at 3 lines); an old history file restored by hand (copy or move keeps its old write time) or a bulk file is never imported (the capture lane's restore probe found the earlier rule imported it). Limit: re-running a command already seen just after recreating the file is missed (fails closed).
- **VS Code's terminal is not a terminal for C22.** Its key runs come from `code.exe`, which is also the editor, so an Enter there is a line of code as often as a command; PowerShell typed in it still reaches the log through the history file.
- **C19.3 dwell share.** The catalog's "dwell per window" is covered by C19.2's per-window screen share; the per-activity feature "dwell share" is read as the share of the activity the pointer was at rest (no shaped sample within 1 s). Speeds come only from gaps ≤ 1 s, so a rest is not slow movement.
- **Pointer input belongs to the activity.** Accepted pointer events open the track's document like any other input, so a mouse-only activity still gets a document (with features and no text). The index keeps its features; it has no chunks to search.
- **A click target that arrives after its activity closed** (the click switched windows) is still recorded in the vault as the click's `Target` record but does not join the next activity's document. Holding a closing document open for 100 ms was rejected: it would delay every boundary for a rare case.
- **The hook benchmark times the callback's managed work** (decode + ring write) on synthetic input, not the native transition: a timer inside the real callback would itself cost time in the path being measured. The real-PC check runs it at 1000 Hz with the machine under normal load.
- **Visibility events.** The spec's triggers (foreground, move-size end, minimize) plus the issue's show / hide and top-level location changes (Win+arrow snaps and maximize fire no move-size event). Location changes arrive for the cursor too, out of context; the callback drops them on `idObject` before any call, and the debounce caps recomputes at 4 a second.
- **UIA view key.** A UIA view is (top-level window, root ref 0): the walk is of the window's root. Tabs inside one native app share a view until a later walk scopes to a sub-container; the diff still only stores changed lines.
- **UIA focus window.** The focus event's window is the foreground window at the time of the event (many focused elements have no window handle of their own); events from Tasktor's own process are ignored.
- **Text-body lines.** A text body's visible text is split into one line per row with refs keyed by content (`RefMinter` on the text), not by position, so a terminal scroll yields the new rows rather than a full re-diff. Lines count against an 8 KB budget per read, not against the 400-element cap.
- **Walk debounce cap.** Changes are debounced 750 ms after the last one but a walk is due at most 2 s after the first, so a constantly changing window (a ticking clock) is still walked; the churn filter then drops volatile refs.
- **SMTC projection.** CsWinRT through the `net10.0-windows10.0.19041.0` TFM (as the Flyout), not hand-written WinRT ABI: SMTC needs typed event delegates and async operations, which by hand means parameterized-interface IIDs. `tasktor-capture` ships self-contained (release.yml publishes it single-file, not Native AOT), so the projection's runtime pieces are fine there; its test project moved to the same TFM.
- **Audio sessions are re-read each second** instead of registering `IAudioSessionNotification`: the spec reads peaks at 1 Hz anyway, a snapshot is cheap, and no callback object (another hand-declared IID) is needed. Peaks are posted only for active sessions.
- **AUMID → app.** SMTC names a source by AUMID, audio sessions by pid. Both meet on the lower-cased exe: browsers' short AUMIDs (Chrome, MSEdge, …) map to their exe; an exe path to its file name; a packaged app to its package family (its audio then matches only if its exe-based id is the same, so a packaged player may show metadata without audible until a real-PC check says otherwise).
- **Agent children's command lines are read by the agent process**, which already reads command lines once per new process for B's script-host matching; they cross to `tasktor-capture` over the local control pipe and are kept only there, so the agent holds no copy and logs nothing. Short-lived children that start and end between two 60 s scans are missed (the spec's honest gap).
- **Exit codes are not read.** With Windows Terminal's marks on, the marks live in the terminal's buffer and no API exposes them to another process (UIA's text pattern has no marks), so C22.3 is the offer and its preview only; recorded commands carry no exit status.
- **Embeddings live in the encrypted index, not in `emb\YYYY-MM.i8` shards.** One SQLCipher database already gives encryption at rest with the index key, forget in the same transaction as the chunks, and a date-range scan through `emb_start`; separate shards would need their own encryption and forget path for the same effect. Revisit if a year's vectors make the scan slow (the spec's estimate is ~40 ms for 90 days).
- **One int8 scale per vector**, not per dimension: per-dimension scales need a calibration pass per model; with L2-normalised vectors the cosine error measured in the tests stays under 0.02.
- **G8 gates use, not code.** The encoder is never downloaded: the owner places a MiniLM-class `model.onnx` + `vocab.txt` in `capture\embedding\`, runs `g8` on the labelled check set and saves its report as `g8.json` there. Without a passing report nothing is embedded. The activity-level embedding for workflow learning (mean of chunk vectors, §9) waits until G8 has passed on real data.
- **The embed worker is started by `tasktor-capture` as a plain BelowNormal process** with a timeout, not in a Job Object with the 25% CPU / 1.5 GB caps (that runner lives in the agent's process control). It runs one batch of at most 256 chunks per 30 minutes.
