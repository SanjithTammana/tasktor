# Optional Windows Widgets package (draft)

This optional project is outside the solution and does not change the portable release. `dotnet msbuild Tasktor.Widget.Package.proj -t:Build` builds the provider. The separate `PackWidget` target publishes the x64 provider and invokes the Windows SDK's `makeappx` to create an unsigned development MSIX; it neither signs nor installs the package. This path has not yet been validated with a real package or Windows Widgets host. The manifest uses a development-only identity and publisher, not a release identity.

Before `PackWidget`, supply `StoreLogo.png`, `Square44x44Logo.png`, `Square150x150Logo.png`, `TasktorIcon.png`, and accurate `SystemScreenshot.png`, `JobsScreenshot.png`, and `WorkflowScreenshot.png` in `ProviderAssets`, or set `WidgetAssets` to their directory. Supply correctly sized genuine assets; none are fabricated here. Set `MakeAppx` if the Windows SDK is installed elsewhere. Replace the development identity and publisher for a real release and arrange signing separately. `AppxManifest.xml` is the draft used by the project. Jobs and Workflow show aggregate sentences only; customization, deep links and actions are not implemented. Host testing requires a properly signed installed package; none has been installed or registered here.

COM lifetime: the server exits when the last COM reference is released, not when widgets go idle (`ServerLifetime`). Each provider exposes `IExternalConnection`, so COM's stub manager reports every strong connection; those connections, `LockServer` and a creation pin from `CreateInstance` to the first connection are the process count COM keeps (`CoAddRefServerProcess` / `CoReleaseServerProcess`). The release to zero suspends the class object, so a new activation starts a fresh server, and a creation already inside the factory gets `CO_E_SERVER_STOPPING`. There is no idle timeout. Nine synthetic tests cover the counting. A cross-process probe of the unpackaged x64 provider (an ephemeral class registration, no registry or package) activated it, kept it alive while held, and saw it exit with code 0 about 26 ms after release.

Deactivation: membership changes cancel stale pulls and wake the loop, and no update follows the next check. One update that has already passed its check can still reach the host just after `Deactivate`; the Widgets contract lets a provider update a widget at any time, and blocking the host callback on that call could deadlock against a host that holds its own lock across it, so this is bounded by design rather than locked. All payloads are aggregate-only.

Still unverified: none of this has run under the real Widgets host, which needs a signed, installed package. Do not treat the draft as production-ready until it has.
